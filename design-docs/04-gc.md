# 04 — Garbage collection / shallow snapshots

**Status:** DONE (phases 0–4 + regime-2 stable-frontier policy); regime 3 (decentralized) deferred
**Roadmap item:** #6
**Depends on:** the op-log (`Crdt.OpLog`, `Crdt.OpDoc`), frontiers, `materialize`.

## Shipped (phases 0–3)

- **`Crdt.OpLog.compact : Node -> Frontier -> OpStore -> (Node, OpStore)`** —
  folds ops ≤ cut into `base`, returns the new base + the remaining store.
  Read-equivalence (`materialize base store == materialize base' store'`) is
  **fuzzed**, not just example-tested.
- **`Crdt.OpDoc.gc : Version -> OpDoc a -> OpDoc a`** — adds a `baseFrontier`
  field; folds ≤cut history into `base`, drops those ops. Read model unchanged;
  time-travel below the cut is gone (the trade). Clock stays safe (folded stamps
  still count toward `Node.maxCounter`).
- **Snapshot-transfer wire** — `encode`/`encodeSince` send a tagged payload:
  `ops` normally, or a `snapshot` (base + frontier + tail) when the peer is behind
  `baseFrontier`. `decodeInto` accepts either, adopting a strictly-ahead snapshot
  base. So GC coexists with delta sync across peers.
- **In-memory `Doc.merge` uses the same base-adoption rule.** Op-union alone is *not*
  enough when the incoming document was compacted: history it folded into its base is in
  no store, so a plain union silently drops it. `merge` therefore mirrors `decodeInto`'s
  snapshot branch — if the incoming `baseFrontier` strictly covers ours, adopt its base,
  keep only our ops above that frontier, and re-materialize. The one case neither path can
  resolve is two documents compacted **independently** at cuts where neither covers the
  other: each base holds folded history the other lacks and a result carries one base, so
  the local one wins. That only arises by compacting below a non-stable cut, which is
  already documented as unsafe below.
- **`encodeFrom cut doc`** — compaction as a **non-destructive export**: it runs the same
  `OpLog.compact` transform at `cut` but ships the result (as a `snapshot` payload) instead
  of installing it into `self`, so the source keeps its full history. Same operation as
  `compact`, opposite disposition (send vs. shrink-self). Enables *keep-full-locally /
  send-peers-a-shallow-copy* and *privacy redaction* (a payload with no ops below `cut`,
  hence no record of edits/authors/superseded text below it). It drops history below the
  cut, not state still live at the cut (which is in the exported base).
- **Tombstone compaction (phase 4)** — when a `compact` folds in the **whole** store
  (`compact (version doc) doc`, so no tail op can still anchor to a tombstone), each
  `Seq`/`Txt`/rich-text RGA in `base` is physically rebuilt from its live elements as a
  right-spine (`Rga.compactTombstones` / `Node.compactTombstones`): dead tombstones are
  gone, the visible value is byte-for-byte identical, and element ids survive (cursors
  keep resolving). With a tail left above the cut, tombstones are kept (a tail op could
  anchor after one). Measured: a list of 200 with 190 deleted shrank from ~98 KB to
  ~5.7 KB encoded (**~17×**) — this is where monotonic growth finally stops.
- **Re-delivery across the boundary** — applying an op is not idempotent on its own;
  idempotence comes from the *store* (`addedFromCandidates` skips what we already hold), and
  compaction removes ops from the store. So a peer re-sending ops we already folded used to
  re-apply them, and that is destructive, not a no-op: `Rga.insertElement` rebuilds an
  element from the op's own seed, reverting every later write into it, and `base` holds the
  rebuilt tombstone-free spine, so replaying originals can change the derived Fugue order.
  Two guards, because each covers what the other cannot: **(1)** `version` names
  `baseFrontier` alongside the store's tips, so a peer's `opsAfter` walk stays resolvable and
  it stops re-sending (without it, our post-compaction edits are the only tips we advertise,
  the peer can't resolve them, and it concludes we know nothing); **(2)** `rebuildIncremental`
  drops incoming ops that its own `base` already holds (`dropFolded`, the wire counterpart of
  the filter `merge` already had), which does not depend on the sender — a full `encode`, a
  relay replay, or an older peer can all still offer folded ops. The residue is a
  deliberately **sparse** batch, where the ancestor walk cannot prove an op is below the cut;
  closing it needs the receiver to remember which op ids it folded, trading away the memory
  GC exists to reclaim.
- Tests in `tests/GcTests.elm`: read-equiv (incl. fuzz + mid-history cut),
  the two re-delivery guards above (an empty delta is offered; a peer's full re-encode
  cannot clobber a post-compaction edit),
  lagging-peer merge after compaction with no resurrection, in-memory `merge` across a
  compaction boundary (base adoption, commutativity, idempotence, agrees with the wire
  path), clock safety,
  cursor-anchored-below-cut still resolves, fresh-peer snapshot catch-up, continued
  convergence afterward, and (phase 4) byte-size collapse, cursor survival across a
  tombstone rebuild, cache-consistency (`== full re-materialize`) after compaction, and
  lagging-peer convergence after tombstones were dropped.

**Soundness is the caller's job** (unchanged from the plan): `compact` never loses
info `materialize` would use, but because `merge` is op-union, *discarding* ops (and
now *dropping tombstones*) is only safe across replicas below a **stable** cut. Both
share the identical envelope; single-replica / pre-persistence GC (`compact (version
doc) doc`) is always safe, which is also exactly the full-store case that triggers the
tombstone drop.

- **Stable-frontier policy (regime 2)** — `Doc.stableFrontier : List Version -> Doc a ->
  Version` computes a **multi-replica-safe cut**: the frontier of the intersection of the
  given peers' ancestor sets, i.e. the causal point every one of them has delivered past.
  Compacting below it drops no op a listed peer still needs (an op even one lacks is kept;
  unshipped concurrent work is nobody's ancestor). The library computes the frontier; the
  app supplies the peer list. `Doc.encodeVersion` / `decodeVersion` (a `Version` is a tiny
  frontier) let peers exchange versions over any transport. A peer **omitted** from the
  list (offline/lagging) isn't protected by the cut, but that's safe — on reconnect it is
  behind `baseFrontier`, so the wire layer catches it up with a **snapshot** instead of a
  delta. So the worst case of an aggressive cut is a heavier catch-up for a straggler,
  never lost data. Tested in `tests/GcTests.elm` (synced-peers cut, concurrent-work
  survives, convergence after a stable-cut compact, lagging-peer snapshot catch-up, empty
  list = no cut, single-peer = regime 1). The demo wires it end-to-end: peers broadcast
  `version`, the "compact shared history" button folds up to the stable frontier
  (`demo/e2e/compaction.spec.js`).

Deferred: **regime 3** (fully decentralized GC without a shared relay/coordinator — a
distributed version-vector agreement protocol; a separate project). Also not yet pruned: a
movable-list's / tree's own tombstone **sets** (deleted valueIds / nodeIds) — only the
`Seq`/`Txt`/`Rich` RGA tombstones, which the footprint benchmark shows dominate; nested
content inside `Mov`/`Tree` is still recursed into and compacted.

## Problem

The op store only grows. Every edit adds an op; deletes are tombstones that are
never removed; text is one op per character. A long-lived document's op set is
monotonically increasing, so memory, materialization cost, and wire size all
creep up forever. GC is the ceiling that separates "works in a session" from
"runs for months."

We want to **replace a causally-complete prefix of the DAG with a single
materialized snapshot**, dropping the ops it subsumes, without changing what any
replica reads and without breaking convergence.

## The trap that makes naive GC unsound

`merge` is **op-union** (`Dict.union` by `OpId`). That is what makes merge
trivially a semilattice — but it means:

> If replica A drops op `X`, then later merges with replica B who still holds
> `X`, the union **resurrects `X`**. A's GC is silently undone, and worse, a
> tombstone that was compacted away can resurrect the element it deleted.

So GC is **not** "delete ops you don't need locally." Dropping an op is only safe
if **no future merge will reintroduce it** — i.e. every replica you will ever
merge with has already incorporated it. In a peer-to-peer system you cannot know
that for free; it requires either coordination or a conservative bound. This is
exactly why Loro frames it as a *shallow snapshot* (a transfer/storage form),
not a destructive delete from a live shared log.

## The model: a snapshot is a moved `base`

The key reuse: `materialize` already folds ops over a **`base` node**
(`OpDoc.base`, currently the schema's empty tree). A snapshot is just:

> **base' = materialize base (ops causally ≤ F)**, then **keep only the ops
> *not* causally ≤ F**, recording `F` as the snapshot frontier.

`materialize base' remainingOps` then reads **identically** to
`materialize base allOps` — because folding is associative over a causal order
and `F` is a causal cut. So a snapshot is an equivalence-preserving rewrite of
`(base, store)`, not a semantic change. The read model is unchanged; only the
representation shrinks.

```elm
-- conceptually, in Crdt.OpDoc
type OpDoc a =
    OpDoc
        { … 
        , base : Node          -- was always "empty tree"; now "state as of `baseFrontier`"
        , baseFrontier : Frontier   -- the causal cut `base` already incorporates (NEW)
        , store : OpStore      -- now holds only ops NOT below baseFrontier
        }

gc : Frontier -> OpDoc a -> OpDoc a
gc cut doc =
    -- 1. base' = base + all ops causally ≤ cut, folded in causal order
    -- 2. store' = store minus those ops
    -- 3. baseFrontier' = cut
    -- read model is provably unchanged
```

`OpLog` gains the mechanics:

```elm
ancestorsOf  : Frontier -> OpStore -> OpStore   -- already exists
opsAfter     : Frontier -> OpStore -> List Op   -- already exists (delta sync uses it)

-- new: fold the ≤cut ops onto base and return (newBase, remainingStore)
compact : Node -> Frontier -> OpStore -> ( Node, OpStore )
```

## What keeps it sound: only compact below a *stable* frontier

The whole correctness question reduces to: **which `cut` is safe to pass to
`gc`?** A `cut` is safe iff every op at-or-below it will be present in every store
it could ever merge with — so that dropping those ops can never lose information a
future merge would need, and a re-merge of an old peer's ops below `cut` is a
no-op (they fold to a state already ≤ base').

Three regimes, in increasing capability:

1. **Single replica / local persistence (always safe).** When saving to disk or
   on app start, a replica can snapshot up to *its own* current frontier: there
   is no concurrent peer for that store. This already delivers the main win
   (bounded on-disk + load size) with zero coordination. **Ship this first.**

2. **Server-mediated stable frontier (safe, needs the relay).** If a peer (or the
   relay) tracks an acknowledged frontier that *all connected* replicas have
   delivered past, that frontier is safe to compact below. The demo's relay could
   compute this. Medium effort; the realistic multi-peer answer.

3. **Fully decentralized GC (out of scope).** Requires a distributed agreement
   protocol (version-vector exchange + min). Real, but a separate project.

The library provides `gc : Frontier -> OpDoc a -> OpDoc a` and **does not decide
the frontier** — choosing a safe `cut` is the application's policy. We document
the safety contract loudly: *passing a frontier that a future merge partner has
not reached can drop ops that partner still needs.* (Even then it only loses
*their* not-yet-merged concurrent work below the cut; the snapshotting replica's
own reads stay correct.)

## Interactions to get right

- **Clock safety.** `base` already contributes to `Node.maxCounter`, and `gc`
  only moves ops into `base` (their stamps still appear there), so the merge-time
  `Id.observe (Node.maxCounter cached)` still advances past everything. Verify
  with the existing clock-safety property.
- **`causalOrder` over a snapshotted store.** Remaining ops may have `deps`
  pointing *into* the snapshot (now absent from `store`). `causalOrder` already
  tolerates deps outside the store (it counts only in-store deps), so a
  snapshotted store still linearizes correctly — but we must confirm the dropped
  deps were genuinely folded into `base`, else an op could apply before its
  (now-in-base) prerequisite. Since `base` already *contains* the prerequisite's
  effect, applying the remaining op onto `base` is correct. Test explicitly.
- **Delta sync after GC.** `opsAfter F'` for a peer behind `baseFrontier` can no
  longer be answered with ops (they're gone) — the peer needs the **snapshot**
  instead. So the wire protocol grows a "snapshot + tail" message: if a peer's
  version is below our `baseFrontier`, send `(base, baseFrontier, opsAfter
  peerVersion)`; otherwise send ops as today. This is the same shape as Loro's
  shallow-snapshot transfer.
- **Checkout/time-travel below the snapshot is lost.** Once ops below `cut` are
  gone, you can't `readAt` a version older than `baseFrontier` (the ops to replay
  are gone). That is the fundamental trade of GC — document it; checkpoints below
  the cut become unreadable. (Loro: same — shallow history.)
- **Cursors below the snapshot.** A `Cursor` anchored to an element whose insert
  op was compacted still resolves, because the *element* lives on in `base`
  (snapshot is state, which includes live elements + retained-as-needed
  tombstones). Only the *op* is gone, not the element. Test.
  **Except when the element itself is gone:** if the anchor character was deleted
  and the tombstone pass then dropped it, no position remains to resolve against.
  `cursorOffset` returns `Nothing` there rather than guessing — a walk that never
  meets its anchor otherwise returns the live count, i.e. a caret silently
  teleported to the end of the text. Cursors are ephemeral presence data, so the
  peer's next broadcast resolves normally; the caller just draws no caret for one
  frame. (Same answer for an anchor whose insert has not *arrived* yet — with
  non-causal delivery that is the same unplaceable case.)
- **Local undo/redo below the snapshot.** An `UndoEntry` is a version *range*
  whose inverses are recomputed from the ops each time (never frozen — see
  design-doc 05), so it dies with them. Worse than dying loudly: `inverseBetween`
  reads the *store*, so a compacted-away range yields no inverses at all while
  `canUndo` still reports `True` and `undo` still pops the entry — a UI undo
  button that lies. `compact` therefore prunes the stacks, keeping exactly the
  entries whose `before` version is at-or-above everything the cut folded away
  (which also guarantees their `checkout before` is unpolluted by the new `base`).
  Undo of edits *above* the cut keeps working normally.

## Tombstones: the subtle win and limit

A snapshot lets us finally drop tombstones — but only those **causally settled**
below `cut`. A tombstone in `base` can be dropped from the materialized `Node`
*if* nothing that survives the compaction references it. Note that "references"
covers more than the op store: rich-text **mark anchors live inside `base`** and
name character ids, so dropping a tombstone an anchor points at silently zeroes
that mark's coverage. `Node.compactTombstones` re-anchors marks onto the
surviving covered characters rather than assuming `base` is reference-free.
The op-store side of the rule is that no remaining op (or future op below `cut`
from a lagging peer) may reference it.
Under regime (1)/(2) where `cut` is stable, a tombstone ≤ `cut` whose element is
also deleted ≤ `cut` can be physically removed from `base`'s RGA. This is where
the monotonic-growth bleeding actually stops. **Stage this after the snapshot
mechanism works** — it's an extra compaction pass on `base`, separable from the
op-dropping.

## Phased plan

0. **`OpLog.compact : Node -> Frontier -> OpStore -> (Node, OpStore)`** + the
   equivalence property: `materialize base store == materialize base' store'`
   for any `cut`. Pure, no API change yet. **This is the load-bearing proof.**
1. **`OpDoc.gc : Frontier -> OpDoc a -> OpDoc a`** with `baseFrontier` added to
   the record; `read`/`merge`/`cursorOffset`/clock all unchanged-by-construction,
   verified by tests (read-equivalence before/after gc; gc-then-merge-old-peer
   converges; clock still safe; cursor below cut still resolves).
2. **Local-persistence GC (regime 1)** — a `gc (version doc) doc` helper for
   save/load; the safe, no-coordination win. Wire into nothing yet (no
   persistence layer in the demo) but expose + test.
3. **Snapshot-transfer wire format** — `encodeSince` learns to send a snapshot
   when the peer is below `baseFrontier`; `decodeInto` learns to accept one.
4. **Tombstone compaction of `base`** — physically drop settled tombstones.
5. *(Deferred)* server-mediated stable frontier in the relay (regime 2);
   decentralized agreement (regime 3).

## Risks

- **Soundness of the `cut`** is the whole game; the library must not pick it, and
  the contract must be unmissable in the docs/types. Consider naming it
  `gcUpTo`/`unsafeGcUpTo` or returning a `Result` when `cut` isn't ≤ the doc's
  own frontier (a cut you don't even have is always wrong).
- **Equivalence proof under partial deps** (the `causalOrder`/base interaction) is
  the trickiest correctness point — phase 0 must fuzz it, not just example-test.
- **Checkout/checkpoint loss below the cut** is a real capability regression for
  history; make it explicit and let the app choose how far back to keep.
